# AGENTS.md

Guidelines for anyone, human or agent, working in this codebase. Read this before changing anything. Follow it unless the owner says otherwise.

## What this is

An order, invoice and stock app for an embroidery and uniform company. Its customers are mostly schools, each with many garments, badge placements, house colours and returning orders. A smaller share are individuals with one-off orders, such as Ankara shirts cut from fabric the customer brings.

The app does five jobs:

1. Find a customer and see their history.
2. Build an order from lines, with prices that remember each school's rates.
3. Produce an invoice and a production sheet from the order.
4. Take payments and show who owes what.
5. Keep stock honest: deliveries add, open orders reserve.

A separate 3D studio shows a realistic mockup of a garment with its badges and lettering. It opens from an order line and saves its design back onto that line.

## Two modes, one codebase

Every request runs in one of two modes. This is the most important rule in the project.

| Mode | Who | Database | Writes |
|---|---|---|---|
| `demo` | Anyone, no login | `DEMO_DB` (sample data) | Never |
| `live` | Signed-in users | `LIVE_DB` (the shop's real records) | Yes |

- `getCtx()` in `src/lib/auth.ts` decides the mode from the session cookie. No valid cookie means `demo`.
- Demo visitors can open every screen and press every button. The interface behaves the same in both modes. Only the save step differs.
- Every API route that changes data starts with `requireLive()`. In demo it returns `403 {demo:true}` and the client shows "This is the demo. Changes aren't saved. Sign in to save."
- `run()` and `batch()` in `src/lib/db.ts` throw if asked to write to anything but `live`. This is a second lock behind `requireLive()`. Keep both.
- Pages and queries always take the mode from `getCtx()` and pass it down. Never hard-code `'live'` in a page. Never read the live database for a demo visitor.
- The demo database is loaded only from `data/demo-seed.sql`. No code path edits it at runtime.
- Signing in is how the shop starts using the app for real. The profile circle in the top bar is the only entry point.

## Stack

- Next.js 15 (App Router, React 19, TypeScript), served on Cloudflare Workers through `@opennextjs/cloudflare`.
- Cloudflare D1 (SQLite) for data. Two databases, bound as `DEMO_DB` and `LIVE_DB` in `wrangler.jsonc`.
- `jose` for the signed session cookie. Native `crypto.subtle` PBKDF2 for passwords.
- No ORM, no UI library, no CSS framework. Plain SQL, plain components, one stylesheet.
- The studio is a single static HTML file in `public/studio/index.html` that loads three.js r128 from cdnjs.

Do not add `better-sqlite3`, `bcrypt` or `bcryptjs`. They do not run on Workers or they burn the CPU limit.

## Data rules

- Server components read through the helpers in `src/lib/q.ts`. Add a helper there before writing SQL inline in a page. Small one-off reads inside a page are acceptable.
- Every query goes through `all`, `first`, `run` or `batch` in `src/lib/db.ts`. They take the mode as the first argument.
- D1 has no interactive transactions. Any change that touches more than one row uses `batch()` so it succeeds or fails as a whole.
- Statements use bound parameters (`?`). Never build SQL by joining user text. The only interpolated value is a table name chosen from a fixed map in `api/setup`.
- IDs for people, orders and stock items are short text IDs made by `nid(prefix)`. Order lines and log rows use integer autoincrement IDs.
- Money is stored as whole naira integers. Display it with `naira()`. There are no kobo.
- Dates are stored as `YYYY-MM-DD` text. Timestamps in logs are ISO strings. Display dates with `fmtDate()`, which formats in UTC so the day never shifts. Show clock times in `Africa/Lagos`.
- A schema change is a new numbered file in `migrations/`, applied to both databases. Never edit `0001_init.sql` after it has been deployed.
- Totals are computed, never stored: subtotal is the sum of line quantity times price, total is subtotal minus discount, balance is total minus payments. This keeps invoices correct when lines or payments change.

## Business rules

### Customers
- Kinds are `school`, `individual` and `other`. Only the name is required.
- Schools can carry their own price list, houses and crests. Individuals have no houses or crests.

### Orders and stages
- Stages, in order: `Draft`, `Confirmed`, `In production`, `Ready`, `Collected`.
- Anyone signed in can move an order to any stage, forward or back. There are no per-role permissions. Every move is written to `stage_log` with the person's name and time, and the order page shows the latest moves.
- Leaving `Draft` needs at least one line. It also assigns the invoice number `INV-<year>-<4 digit running count>` and the placed date, once.
- A draft has no invoice number and shows none.

### Editing after confirming
- Once an order is past `Draft`, adding, changing or removing a line needs a reason. The API refuses without one.
- Each such change writes a row to `order_changes` with who, when, what, the money difference and the reason. The order page shows these under "Changes since confirming".
- Setting a line's quantity to 0 removes it.
- The interface says plainly that the production sheet needs reprinting after a change.

### Prices
- `prices` holds the standard price per item. `price_overrides` holds a school's own price with an optional reason.
- When a line is added, the price is the school's override if there is one, otherwise the standard price. The user can still type any price.
- Changing a price affects new orders only. A confirmed order keeps the price on its lines.
- Setting a school's price equal to the standard price removes the override.

### Reorder
- Reorder copies chosen lines from a past order into a new draft. Quantities are editable. Prices are today's prices for that school, not the old ones. The saved mockup travels with the line.

### Payments
- A payment is entered against a customer, not an order. It is applied to that customer's orders with a balance, oldest due date first, as one `batch()`.
- A payment larger than the total owed is refused. There is no credit balance.
- Money owed per customer is the sum of positive order balances, ordered by the oldest due date.

### Stock
- A stock item has an on-hand quantity, a unit (`metres`, `pieces`, `cones`) and an optional warning level.
- A delivery adds to on-hand and writes a `stock_movements` row with the running total, the supplier and the invoice reference.
- Reserved stock in live mode is computed, not stored. For every order in `Confirmed`, `In production` or `Ready`, each line's quantity is multiplied by its garment's `stock_per_piece` recipe. A line matches a garment by exact item name. Drafts do not reserve.
- Available is on hand minus reserved. A negative available shows as "Short by N". Available at or below the warning level shows "Running low".
- In demo mode only, reserved comes from the stored sample figures, because the sample orders are not itemised enough to derive them.
- Stock is not deducted when an order is cut or collected. Only deliveries and counts change on-hand. Keep this in mind before adding automatic deduction.

### Garments, houses, crests
- A garment is stored as JSON: kind, main cloth, sizes, numbered placements (place, what goes there, how) and the stock used per piece.
- Placement numbers are the same numbers shown on the production sheet and in the studio.
- A house has a colour, a jersey cloth and a badge, each naming a stock item. Houses and crests belong to a school.

### Invoice and production sheet
- Both are printable pages. Print styles hide the app chrome so only the document prints.
- The invoice shows lines, payments received, subtotal, discount, total, paid and balance due.
- The production sheet never shows prices. It shows each line with its quantity, size breakdown (typed as `6:2, 8:3`), numbered placements, tick boxes for Cut, Stitch, Finish and Check, and the materials to pull from stock.
- Shop name, address and bank details are placeholders in square brackets until the owner supplies them.

## Authentication

- Accounts are created by the owner. There is no sign-up page.
- On the first sign-in attempt, if `users` is empty, the account named by the `ADMIN_EMAIL`, `ADMIN_PASSWORD` and `ADMIN_NAME` secrets is created.
- Passwords are hashed with PBKDF2-SHA256, 100,000 rounds, a random 16-byte salt, stored as `pbkdf2$<salt hex>$<hash hex>`. 100,000 is the Workers maximum. Comparison is constant time.
- The session is a signed JWT (HS256) in an `httpOnly`, `secure`, `sameSite=lax` cookie lasting 14 days. It holds only the user id.
- Failed sign-ins are counted per IP in `login_attempts`. Eight failures in ten minutes block further tries for that address.
- `AUTH_SECRET` is required. The app throws rather than start without it.
- Secrets live in Cloudflare secrets and in `.dev.vars` locally. Neither is committed.

## The 3D studio

- It lives at `/studio/` and opens in a new tab from the "Mockup" button on each order line, with `?order=<id>&line=<id>&item=<name>`.
- On load it reads the line from `GET /api/orders/:id/lines/:lineId`, then picks the garment from the item name: Ankara, shorts, trousers, otherwise a tee. If the name has no model, it opens the tee and says so.
- It chooses the cloth colour by matching the line's detail text to a colour name, such as "Red house".
- If the line has a saved design it restores it exactly. If not, it opens a clean garment.
- "Save to order" sends `PUT /api/orders/:id/lines/:lineId` with a JSON snapshot of the garment, cloth colours, decorations and Ankara panel settings. Keys starting with `_` are internal and are not saved. The snapshot is capped at 900,000 characters.
- Demo visitors can open the studio and play with it. Saving shows the demo message.
- The studio is procedural. Garments are built from a height field, not scans. Printed patterns are reconstructions. Do not describe it as a photograph.
- The studio and the app share the cookie because they share an origin. Do not move the studio to another domain.

## Interface rules

- The primary screen is a laptop at 1440 by 900. Layouts also hold at phone width with a 16px side gutter and no horizontal page scroll.
- Staff are busy and not technical. Copy is plain and short, in sentence case, with no jargon and no em dashes. Say "Owes" and "Short by 14", not "Receivable" or "Negative availability".
- Inputs are 46px tall and primary buttons 48px. Compact buttons are never under 40px.
- Colour is never the only signal. Status chips carry words, such as "Short by 9", "Running low" and "Draft".
- Visible focus rings on everything interactive. Icons that stand alone have labels.
- Colours come from the tokens in `src/app/globals.css`: teal `#0E5C63` for actions, amber for caution, red for shortages and debts, green for paid and delivered.
- Type is Bricolage Grotesque for headings and Figtree for text.
- Currency is shown as `₦` with thousands separators.
- The top bar is the same everywhere: Customers, Orders, Stock, Reports, Setup, and the profile circle. The demo banner appears above it in demo mode.
- Buttons that save use the shared `useSave` hook. It disables the button while saving, refreshes the page on success, and turns a demo refusal into the standard message instead of an error.
- Every page follows its design board in `project/*.dc.html` (header, spacing, colours, row shapes, chips). Shared pieces live in `src/components/ui.tsx`. Change a page's look only by changing the board first and then the page.
- Forms are plain HTML forms with labelled inputs. Pages are server components. Client components exist only for interaction and live in `src/components`.

## Writing code here

- TypeScript, two-space indent, single quotes, semicolons.
- Next 15 passes `params` and `searchParams` as promises. Always `await` them.
- `cookies()` is async. Await it.
- `await req.json()` is cast to `any` in routes. Validate the fields you use before trusting them.
- API routes return `Response.json({ ok: true, ... })` on success and `{ error: '<plain sentence>' }` with a 4xx status on failure. The error text is shown to the user, so write it for them.
- Validate on the server even when the form validates on the client. Check required fields, whole numbers, non-negative amounts and that referenced rows exist.
- Keep route handlers short. Put reusable reads in `q.ts`.
- No new dependency without a reason that fits on one line. Prefer the platform.
- After editing `wrangler.jsonc`, run `npm run cf-typegen`. `postinstall` does this on install.

## Deploying

1. `npx wrangler d1 create uniform-demo` and `uniform-live`. Put both ids in `wrangler.jsonc`.
2. Apply `migrations/` to both with `--remote`.
3. Load `data/demo-seed.sql` into `DEMO_DB` only. Never load demo data into `LIVE_DB`.
4. `npm run deploy`.
5. Set secrets: `AUTH_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME`.
6. Attach the custom domain in the Cloudflare dashboard.

Back up live data with `npx wrangler d1 export LIVE_DB --remote --output=backup.sql`.

## Testing

Before finishing any change, check the behaviour that matters, not just that it compiles.

1. `npx tsc --noEmit` passes.
2. `npm run db:local` then `npm run preview`.
3. As a visitor, every page loads and every write endpoint answers 403. The demo figures still read: Greenfield owes ₦500,000, total owed ₦773,000, the first order totals ₦480,000 with ₦280,000 due.
4. After signing in, the live database starts empty. Create a customer, an order and lines, confirm it, make a change without a reason (refused) and with one (logged), add a discount, record a payment, try an overpayment (refused), receive stock, and check reserved stock matches the recipe.
5. As a visitor again, none of the live records appear.
6. Open the studio from a line, save a design while signed in, reload it, and confirm the demo refuses the save.
7. Pages print cleanly: invoice and production sheet show no app chrome.

## Sample data

The demo comes from `data/seed/uniform_app_dummy_data.json`. The first order, "First term 2026 intake" for Greenfield Primary School, has all 16 lines (188 pieces, ₦510,000 before a ₦30,000 discount). Its figures are the reference the other screens agree with.

Other demo orders carry one placeholder line each so their balances are right. House and stock figures beyond the first seven stock items are invented and marked as such in the JSON. Keep new sample data consistent with these totals.

## Not in scope yet

These do not exist, and the code does not pretend they do:

- A screen to add more staff logins. Extra logins are inserted into `users` directly.
- A size picker on lines. Sizes are typed text.
- Studio models for pinafore, skirt, tie and cap. Those items open on the tee with a notice.
- Automatic stock deduction when work is cut or collected.
- Customer-facing pages. Nothing is shown to customers.
- Credit balances for overpayment.
